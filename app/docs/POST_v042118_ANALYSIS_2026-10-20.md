# +362 后续逻辑与表达审查（2026-10-20）

本次仅分析，不修改应用、人设、版本、收尾协议或 Android 8 支持，不重新构建。基准为 +362 最终应用源码 91437635（本地 4bbe711 同树）；本次结论不覆盖既有 CI 的通过记录，也不等于真实模型或真机验证。

## 模型对谈打开时的主动聊天

`ModelDialogueRoomPage.initState/dispose` 与沉浸房间一样调用 `setImmersiveChatPageVisible(true/false)`。原生 `CompanionRuntimeState` 共享同一个可见标志，前台和后台桥均读取它。主动引擎在初始评估、实际模型请求许可和生成后检查此标志；普通主动消息和 Cedar 主动分享都受限。因此正常进入具体房间后，主动聊天会被阻止。房间列表页不设置此标志；离开具体房间后恢复通常的主动机制。

仍有共用竞态：`proactive_engine.dart` 在生成后检查可见标志，但之后还有异步操作、交付核验、数据库提交、呈现设置和通知调用。用户在检查通过后才进入房间，`commitProactiveMessageIfCurrent` 没有此标志，原生 `CompanionNotification.postMessage` 也没有最终房间拦截，故在途消息可能仍入库并发通知。此缺口同样存在于沉浸房间，不能把正常路径的屏蔽表述为绝无漏入。尚未做真机竞态复现。建议后续补发送端拦截与在途任务失效，避免只在生成前再加一次检查。

## JEV：低概率第三项仍可能覆盖前两项

确定代码行为：`jev_decision_gateway.dart` 对已报告概率排序后，如果前两项相差不超过 0.10，部分问题直接采用预设中性标签，不要求该标签位于前两名、也不要求其概率足够高。

例如 `chat_intimacy_route / game_attitude` 输入：

| 标签 | 概率 |
| --- | ---: |
| encourage | 0.47 |
| pause | 0.45 |
| none | 0.08 |

应用结果为 `none`。这是按代码推演，未调用真实 JEV。类似策略仍用于任务动作、游戏目标、作品目标、时长等；因此用户描述的问题并未在所有判断入口消失。它是 JEV 结果之后的本地决策，不能归因于 JEV 自身把第三项排在第一位。

已有 `resolvePlayfulGroup` 与 `resolveCedarGroup` 先合并明确属于同一方向的标签，解决了部分“同一意图被拆票”的问题；但分组后的方向接近时也仍可能返回低概率甚至未报告的中性标签。已有测试明确认可某些这种保守回退，所以全量测试通过不会自动发现这个设计问题。

本轮新增的 `tool_route/tool_room_target/tool_room_view` 没有进入上述中性标签表，也没有自定义 resolver：它们采用已报告概率最高项，不会因为 A/B 接近而额外选择低概率 C。稀疏概率只比较已报告项，不能宣称检查了未返回项的排序。

建议将“判断不确定”与“语义明确为 none/chat”分开。只有确实同义、对当前操作具有相同含义的标签才合并；不同房间、相反动作不可合并。只读目标不清时进一步查找或澄清；写操作维持原授权门槛，不能为避免低 C 就统一强选最高项执行。

## 新工具入口的缺口

### 1. 一次摘要读取会过早结束整个工具循环（优先修复）

`durable_generation_runner.dart` 的 `localPlanClosesLoop` 在本地计划全部为摘要读取且有成功结果时即为真，此分支不检查其他尚未完成的目标或是否仍需另一工具。新增语义房间直读扩大了命中范围。

例如“先看看刚结束的对谈，再联网核对其中的说法”，若选择 room/唯一房间/summary，直接读取成功后 `toolsOpen=false`，即使本地关键词已暴露网页工具，也只进入最终回答。两个房间的回顾也只有单个语义目标槽位。此为条件明确的代码路径，尚未用真实 JEV 自然语言复现。应仅在整轮需求确已满足时结束，不能把某个读操作成功当作整轮完成。

### 2. 房间目标的不确定性没有执行层保护

`tool_room_target` 的提示要求有歧义时选 none，但实际 gateway 仍直接用最高概率项。假设 r0=0.47、r1=0.45、none=0.08，会直接读取 r0；`interpret` 不再获得概率或候选差距，无法检查是否唯一。

JEV 也只是补充入口：`semantic.directPlan ?? routeLocally(user.content)` 保留原本地路由；可用工具集合也是关键词集合与语义集合的并集。语义 none 或未解析到目标，并不阻止本地房间解析器继续执行。比如“昨天模型对谈说了什么？”在语义未确定目标时，本地解析可产出没有日期过滤、query 为空的房间读取；reader 将其按最新房间处理。不能把“没有唯一目标”悄悄变成“用户明确要最新房间”。

这里没有发现游戏控制自动改用别的目标的证据：当前控制执行器要求真实 game_id/session_id，不明确则阻止，不能把房间问题扩大宣称成已证实的游戏误操作。

### 3. 相对日期缺乏可靠元数据

新增候选只有标题、话题、状态、updated_at；模型对谈最多 6 个、结束沉浸房间最多 4 个。没有提供当前时间/时区、实际首末发言时间和关闭时间，且改名、暂停等也会更新 updated_at。因此“昨天聊的”和“刚结束的”不能稳定靠更新时间区分，较老房间也可能不在候选中。库中已有实际时间，不应以元数据更新时间替代发言发生时间。建议补充真实时间坐标，未定位时允许搜索扩展候选。

## “接住用户”是否写得过多

检查了当前默认映射与用户 2026-10-19 07:25 备份中的实际规则。备份不是 10 月 20 日实时设备状态，但与 +362 没有改动的世界书正文相符。

不能把仓库保留的旧大段文字都算作正在叠加：当前 `02_daily/03_behavior/03_personality_seed/01_relationship` 的对应正文已清空。核心身份明确“不是服务者”，回应、拒绝和行动来自自己的判断与意愿；实际启用的“对话活人感”允许只接半句话、略过枝节、自己联想、带过或换题、让话题停下。必要内容完整的要求主要针对明确办事、事实查询和认真求助，没有发现常驻规则普遍要求每条哄好、每个梗都接或每次都顺从。

不过，代码中的表达引导确有收紧倾向：

1. `ConversationInitiativePolicy._userRequestsAnswer` 使用问号加“什么/怎么/是不是”等词判断，命中后注入“先完整回应……再决定是否带一句自己的态度”。例如“你是不是又偷吃 token 了？”也命中，未判断它是否在玩梗。
2. `DialogueExpressionPlan` 按关键词指定责任；仅有“bug/设置/版本”等词也可能变成任务。例如“哈哈，服务器又出 bug 了”会得到任务指引。规则本意是防漏答，但会把部分聊天推向办事方式。
3. JEV 的 serious 类把 practical help 与需要照顾/停止玩笑放在一起，可能压低轻松问答中的玩笑空间。这是分类粒度的风险，不能仅凭提示文字断言实际误判率。
4. 普通用户轮要求非空正文；空内容会被视为错误。群聊卡的“安静结束、什么都不发”需要独立运行协议，当前不能仅靠增加一句人设文字实现。话题可以停在短回复，不等于可以完全不回复。

用户提供的是群聊角色卡：在多人消息流里不抢话、只挑自己有兴趣的内容有直接作用；它自己也规定被点名或直接问到时先回应，事实问题需要查证，并非统一拒绝“接住”。值得借鉴的是有限注意力、自然的不配合、偶尔没接住梗和不必续聊；“故意答错、假装办事、把明确求助乱回”会削弱本项目的工具与记忆可靠性。固定 1–10 字、出现某词即失败等也会形成另一套机械模板，不宜整卡复制。

后续如果调整，优先审视问句/任务的机械分类与过强的先后顺序，把实际任务完成度和情绪是否顺着用户分开，避免继续堆“更自然”或“别接住”禁令。本次不调整人设。

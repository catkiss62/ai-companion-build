# 小改动与持续维护流程

## 开始任务

先确认实际分支/HEAD、唯一总账顶部与用户本轮范围，再读一张相关维护卡及对应源码片段。历史只按关键词扩展。入口图帮助定位，不能替代阅读实际调用者；不要为了一个 UI 或提示词修改顺带重构共享调度、数据库或原生接入。

任务开始和结束均更新 [唯一总账 v4](../ledger/AI_Companion_总账_v4.md)。状态明确使用“讨论/方案、已实现、本地验证、CI通过、真机通过”；真机通过注明设备和测试范围，不从无反馈推断整版正常。

## 给其他 AI 的最小任务包

提供仓库和明确分支、起始提交、目标行为与复现步骤、相关维护卡、允许修改范围、必须保留的行为、选定测试及交付要求。例如作品重复卡片：先看 CREATIVE 卡，再检查近期作品材料与想法分类，列出预期多样性，不先改共享聊天规划器。

优先以一个能独立回退的提交完成一项小改动。模型能力不足时缩小任务；涉及事务、并发、恢复或模型路由的变化需扩大验证，不能仅凭“改动行数少”判断风险。

## 同一任务的文档更新要求

| 改动类型 | 同步位置 |
| --- | --- |
| 新功能、入口、模块职责或调用关系 | 对应维护卡；新领域才新增卡并更新 INDEX |
| 上下文/输出限制、模型选路、状态/恢复规则 | 对应卡的边界说明与回归入口 |
| 新设置、用户可见行为或能力取消 | App 帮助 `app/lib/features/settings/capability_help_page.dart`；必要时相关 UI 说明 |
| Agent 能做什么、何时可用及权限变化 | `app/lib/core/agent/agent_self_reader.dart`；工具声明及后台能力分别核对 |
| 新的已复现回归及修复 | 回归索引概括结论并链接原始证据；维护卡加入真实测试 |
| 每次任务的过程、失败路线、实际验证和待验 | 仅写唯一总账，不另建滚动进度账 |

与 App 帮助或自查无关的纯内部修改，可在总账记录“已核对，无用户可见能力变化”。确实需要更新但本轮未实施的，列出缺口、理由和续办入口；不能用修改维护文档代替修改实际帮助。

## 历史资料处理

维护卡优先描述当前核对行为；版本专题保留当时证据。重复尝试归纳成回归条目，但保留原始失败路线、版本、测试和用户确认。旧方案先加状态标签，不凭“未直接引用”删除。冻结归档不改字节；根 v2、v3 不继续写新任务。

注释优先解释不直观的原因、约束和副作用，例如为什么游标必须按实际覆盖推进；不为每行代码加翻译式注释。若资料和源码不一致，分别记录实现事实与待决设计。

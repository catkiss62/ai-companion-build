# QQ 定向复查：+384 基线与下一阶段接口

日期：2026-10-27（Asia/Shanghai）。状态：**检查与方案记录完成，尚未实施修补**。

基线 v0.42.140+384 / schema63；运行源码 `20dba209b6c8a2464296fc2c22e571f93a24d73a`，tree `291a5fba06207d01c2dd30662c7b349f268732ba`。远端交付文档头 `2bd0c5c6a9209cfa131656ad2a43868fa7d289ff` 与本地 d8bfd295 同树。本轮不修改功能代码、模型配置、数据库版本、工作流或 APK，也不展开七类大检查。

## 范围与证据边界

检查了 QQ 接收/去重/分批领取、回复模型与取消、图文/分条投递、后台服务恢复、本人身份与群公开授权、只读 App 记忆、QQ 原文/来源笔记/分享、按月管理、编辑删除、导出导入与旧群话题过滤，并对照现有相关回归。

本轮执行的是 [合成证据脚本](review_probes/qq_v042140_probe.py)，结果见 [JSON](review_probes/qq_v042140_probe_results.json)：从基线文件提取 QQ 建表语句，在内存 SQLite 上执行关键状态转换；另对分条算法和取消回调条件作受控复算。配置写入与 Android 回调的反例是根据真实调用点安排的交错，**没有在 Android/加密存储运行时复现**。脚本绑定基线源码哈希，不是未来修补的生产回归门禁。

当前容器没有可用的 Flutter SDK；本轮没有新跑 Flutter、原生测试、CI 或真机，也没有调用付费模型/发送真实 QQ 消息。+384 已通过的 2850 全量、1295 专项和170存档恢复仍是该次交付的证据，不能冒充本轮新反例的验证结果。

## 结论

确认四项需要在新增能力前处理的基础问题，以及两项条件性/长文本边界。它们不等于六个已发生的真机故障，也没有证据表明私人完整记忆已被直接送进群模型。

### R1：接收时身份与生成结果的失效版本耦合

位置：`qq_runtime.dart:136,196–199`、`qq_store.dart:30–31,64–74`、`qq_archive_admin.dart:51–55`。

接收原文时保存的 accepted_identity 含会话的 `qq_archive_epoch_v1`。编辑/删除笔记和范围清理会递增这个版本，用于阻止旧派生结果写回。之后领取新消息又把它与当前完整身份 JSON 做严格相等比较；不相等时，即使原文未删除、账号和授权未变，也会推进 checked_seq 并返回空。

合成结果：编辑前待处理1条；版本变更后接纳0条、待处理0条，原文仍在。发送前的上下文失效保护本身有价值，问题是把它同时用于否定尚未开始处理的输入。删除预览之后新到、按 throughSeq 保留的消息，也会遇到同一路径。

修补方向：分开“输入属于哪个账号/存档/授权”与“这次生成依据哪个内容版本”。账号、存档代次、上下文重置及授权变化仍使旧任务失效；普通笔记编辑不应静默吞掉尚未领取的有效输入。已生成的过期正文与已经发出的分条继续按现有防重规则处理，不自动重发。

必要回归：同会话编辑旧笔记时保留排队新消息；清理预览之后的新消息仍能处理；另一群不受影响；旧存档/解绑/权限撤回仍拒绝旧任务；已发送部分不补发。

### R2：删除正文也删除了唯一的接收去重依据

位置：`qq_store.dart:42–49,105–114`、`qq_archive_admin.dart:120–129`；接收时限在 `qq_runtime.dart:140–141`。

平台事件身份只依赖 qq_archive.id 的唯一记录。按范围删除或清空会话删除它之后，相同平台 ID 再进入接收路径会得到一个新的本地 seq，并可再次进入判定/生成。合成结果为原 seq1 删除后，相同事件重新成为 seq2 并被接纳。

这个反例需要“近期删除＋平台重送＋事件仍在当前4分钟接收时限内”，不能推广成旧月份清理后所有旧消息都会重放。确认的是原文复活、重复处理和投递尝试；QQ 自身另有 msg_id/msg_seq 去重，所以不能直接断言屏幕上一定出现两份回复，见[官方群消息接口](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_messages.post.html)。

修补方向：接收去重保留独立的最小事件回执/删除标记，只留不含正文的事件摘要及必要期限，不随原文删除。不要为此保留已删除的正文或图片，也不要只依赖平台去重来避免重复付费。导入仍不得恢复发送权限。

必要回归：近期范围删除/清空后，同 ID 重送不重新入库、判定或发送；相同文字但不同平台 ID 仍是新消息；保留的回执不携带原文，具备容量/期限清理；重启与读档后也不复活。

### R3：失败防循环与“已整理完成”被当成同一位置

位置：`qq_store.dart:115–135,165`、`qq_runtime.dart:346–377`；既有合同 `qq_group_runtime_v042137_test.dart:335–339`。

claimSummary 在读取密钥、调用模型和 saveNote 之前，已把 summary_checked_seq 推过该批。密钥未配置、接口失败、关闭连接或提交失效时，普通批次没有持久的待完成记录。

合成结果：三条来源领取后失败，原文仍有三条；再调用没有待整理内容；后来加入第4条，下一批只取第4条，前三条并不会随新消息补上。这里是整理覆盖缺口，不是原文丢失。

这是既有防反复付费的取舍，现有测试明确要求失败批次不在空闲时无限重试；+384 并未新引入该行为。因此修补不能简单回退游标或加一个每分钟重试循环。

修补方向：把“已尝试”“已完成（包括成功判定不值得记忆）”“待重试/已放弃”分开记录。只对确有未完成记录的任务进行有次数、退避和权限检查的重试，必要时提供明确的手动重试入口；JEV 参与判断仍只由新消息触发。不能因找不到笔记就自动重学全部原文，否则会撤销用户删除/空结果的意义。旧缺口无法可靠判断的部分应保留原文，按用户选择范围补整理。

相关调度优化 O1：正常整理每次最多取20条，但只有跨月修复批次会成功后主动继续排队；重启也只唤醒 valid=0 的修复笔记。普通尾批/被打断的5分钟空闲计时可能一直等下一次新消息。应随同上述待办状态收拢，而不是另开一套周期扫全库逻辑。超长单条资料如果仅渲染了局部，也须确认覆盖范围后再标记完成。

必要回归：503、缺密钥、关闭/重连、功能开关和提交失效后可按策略恢复；成功空结果不重复付费；明确删除不重建；21条以上及跨月尾批可完成；无新消息不重复群聊判定；旧代次回包不回写。

### R4：QQ 配置存在跨入口的整份旧快照覆盖

位置：`qq_options.dart:20–35`；App 开关保存 `qq_groups_page.dart:55–60,75–82`；后台认主写回 `qq_group_binding.dart:69–76`，本地确认 `36–52`。

两个入口均先读 QqOptions，再 copy 一个字段并保存整份 JSON。没有跨 Engine 的版本比较/更新串行化。受控交错可以是：后台先读旧设置；用户关闭分享或关闭某群并保存；后台随后把确认本人后的整份旧设置写回，把刚关闭的字段恢复成旧值。这不是群友用提示词认主，而是两个已授权操作之间的丢更新。

另一个交错是 A写数据库策略标记、B写标记、B写加密配置、A写配置；最终标记与实际配置不一致。当前发送检查会因此停止，属于失效即拒绝的保护，但可能让 QQ 持续不回复直到重新保存设置。

修补方向：统一宿主的配置修改入口，使用有版本的字段补丁更新，不能把调用者的旧整份快照直接覆盖当前值；更新中与完成状态需要明确衔接，权限撤回不能被迟到写回恢复。维持加密/本机授权边界，不把认主、群授权直接变成可从存档恢复的普通设置。

必要回归：后台确认本人同时关闭群/分享，各自合法更新均保留，撤回不回退；公开卡编辑与映射更新不互相覆盖；中间写失败能明确恢复/提示，保持失效即拒绝；解绑/换命名空间后旧操作不能改新配置。

### R5：语义分条之后仍有第二次硬切

位置：`qq_reply_parts.dart:12–16`、`qq_reply_delivery.dart:17`、`qq_session.dart:254–257`、`qq_runtime.dart:293–296`。

选择条数最多3只限制了解析数组；实际发送又逐条调用1800字符切分。两条1801字＋一条1700字，共5304字符（含换行），通过5400总量检查，却变成5条平台消息。若再发生图文兼容降级，还可能增加发送次数。正常短回复一次生成、完整分条、1–2秒随机等待的既有行为不受此反例否定。

修补方向：发送前建立一次完整的投递计划，校验每条长度、语义分条数、图片及降级后的总预算；不默默把用户要求的完整消息硬切成更多份。罕见超限用明确、有界的格式失败处理，不为了凑3条截断内容，也不把每条改成一次模型调用。平台被动回复有次数限制，未来涂鸦应一并纳入该计划。

必要回归：1/2/3条短消息；三条长文本；无分隔符长文本；图片兼容降级；中途取消/未知投递；不能在发现计划超限前就先发送一半。

### R6：取消自动保持未撤销之前安排的回调

位置：`QqPrivateService.kt:124–130,137–148,182–185`。

自动恢复定时回调只看 alive 与 enabled；取消自动保持不会关闭 enabled。因此在退避期间取消勾选，之前排队的回调仍可启动一次运行实例。已发出的 ping 超时也只核验原 Engine 是否仍相同，没有重新核验保活勾选；如果此时取消保活、ping未返回，超时仍能进入 failed，再因 auto=false 关闭连接。

这不是“点击关闭连接后仍一定重连”：显式关闭有 enabled=false 保护。反例只涉及取消自动保持但没有点关闭连接，以及已在途的恢复/监测回调。已有原生测试销毁了安排重试的服务，没有推进取消后的定时回调；本轮仅作条件反例，未执行真实 Handler。

修补方向：恢复操作带本机代次/取消令牌，取消选项、手动停止或替换运行实例时作废旧回调；执行时再核验当前授权。正常在线取消保活不应顺带关闭现有连接。

必要回归：退避期间取消、ping等待期间取消、取消后重新勾选、手动关闭、旧 Engine 的迟到回调、凭据永久错误。使用受控时钟推进到回调触发后断言，不只检查触发前标记。

## 本轮未发现新增直接缺口的边界

- 普通旁听批次在事务中领取后，空闲/重启不会反复跑 JEV；native ping 与 QQ 心跳不是模型调用。R2 是删掉去重依据后的特殊路径，不能把两者混说。
- 群回复的正文和图片观察只用本群内容、手工群人格与明确公开资料；完整 App 私人层走本人私聊分支。群友文字/昵称不会直接修改程序的本人映射；`QqPrivateConfig` 把绑定用户单独按 namespace 存储，也避免了普通模型通道保存直接覆盖绑定用户。
- QQ 写入模块没有调用主 Desire/人格成长流水线；本人 App 主动讨论群事产生的私人互动应继续按 App 原规则处理，不能因此禁用普通任务。
- 发送结果未知时没有盲目兜底重发；后续分条会在等待后重新检查状态。已经进入平台的请求无法由本地取消撤回，不能把这一点当作本地重发漏洞。
- 编辑笔记递增修订、删除撤销分享及来源核验、跨月保留原文后撤下旧笔记、读档关闭连接并清除旧待发资格的路径仍在。R1/R2/R3 针对这些操作与队列交错的遗漏，不是说所有保护均失效。
- 月份只是管理与展示层；历史月份仍可检索，没有发现月初自动清空会话的路径。“本月＋上月”也不等于严格固定60天窗口，不应宣传为已经实现了固定天数的裁剪。

这些是本轮源码与既有回归所支持的范围，不是对所有模型措辞、平台行为、手机后台限制的保证。

## 下一阶段接口建议（未实施）

### 群聊学习

单独的群聊表达档案：按账号/会话隔离，保留来源、修订与启用状态。学习句长、接话/玩梗方式等表达特点，不把群友的身份、命令、事实或价值判断直接写成人格规则；排除她自己发出的文字/涂鸦，避免自我循环学习。

仅群聊最终正文读取有界的风格投影；不改 App/本人私聊人格、主记忆、欲望或认主授权，不让学习资料控制是否拥有工具/权限。保留查看、修改、关闭、删除与备份恢复；删源后相应派生资料失效。控制授权与可更新的风格/笔记使用不同版本职责，避免再次出现 R1。

批量、低频提炼，只处理新增且未消费的样本；与回复判断、记忆整理分别记进度，不能把“新消息才判断”扩成“任务失败就永远丢掉”。普通回复优先，学习任务不能占着全部 QQ 队列让私聊过期。

### SVG 小涂鸦

独立的生成与渲染模块，向既有 QQ 投递器提交受控图片结果。跟随第一通道当前模型/思考设置，不写死型号、不额外降低力度；仅明确请求或符合低频参与条件时生成，普通聊天不额外进入 Agent 循环，也不靠无新消息的定时轮询反复决定。

SVG 是不可信图片描述：限制尺寸/复杂度，禁止脚本、外部资源和页面工具桥，转换为 PNG 再走现有上传接口。群内取材只使用本群与公开资料。文字、表情和涂鸦共享本轮投递预算及取消/去重/实际回执；生成成功不等于发送成功，发出后只把实际结果记为她的 QQ 经历。

原文档案继续使用文字观察/描述；PNG 不应无界进入备份。SVG 源和临时图的保留策略应在实现前明确，不把涂鸦直接塞进主作品系统或主成长流水线。

### 执行顺序

1. 先为 R1–R4 补生产入口的失败回归并修基础；R6 的取消许可检查也应在开启更多后台任务前补齐。SQL/条件证据不能代替这些回归。
2. R5 与新的涂鸦投递计划一起收口；两项新能力独立实现、分别验证，不大改已验证的 App 记忆/梦境/作品主流程。
3. 最后做一次 QQ 联合回归：接收去重、风格仅群聊、涂鸦媒体、重连/取消、删除/编辑、保存/恢复、私人资料边界。再集中构建 APK；若基础修补先需要紧急真机验证，再单独出修补包。

本轮至此收尾，仅同步检查文档和总账；不继续循环寻找假设问题，不自动开始功能修补、新功能实现或构建。

# AI Companion · 手机主机与平板伴随端架构 v1

更新时间：2026-08-30（Asia/Tokyo）

> 本文件是后续“手机对接平板”任务的唯一产品/协议设计入口。用户已从“两台设备完整共同登录”收敛为“一个她、一个手机主脑、若干伴随感知端”。实现前先读本文件和仓库根目录 `AI_Companion_当前总账.md`，不得重新假设平板需要复制完整关系数据库。

## 1. 锁定结论

- 手机 App 是唯一主数据源、唯一 Active Brain 和唯一长期写入者。
- 平板安装同一套代码或兼容的伴随模式，但运行时只启用桌宠、设备感知、短期事件队列和配对控制。
- 平板不保存或同步完整聊天、Memory、Thought、Desire、AI Self、关系历史、相册、日记、Agent Outcome 或 MCP 游戏状态。
- 用户聊天、模型生成、主动消息、记忆整理、自主联网、相册保存和 MCP 行动只由手机执行。
- 平板采集的当前 App、活动类别、屏幕亮灭和经授权的屏幕信息，只形成带来源与 TTL 的短期感知事件；是否进入 Prompt、Thought、Memory 或行动由手机现有主干决定。
- 手机可向平板发送短期桌宠表现指令；这不是聊天数据库同步，平板不把气泡或动作保存成第二份历史。

## 2. 与备份/接管的边界

- 普通 `.aibackup` 只备份手机主数据。添加平板伴随端时绝不导入此备份。
- `.aicomp`、Nearby 接管和 standby/手动接管只用于更换主手机或紧急恢复，不用于平板配对。
- 新入口应称为“添加伴随设备 / 移除伴随设备”，与“备份、恢复与更换主手机”分区显示。
- 手机丢失后由完整备份恢复到新手机；恢复安装先 standby、用户确认旧主手机下线后再接管的保护继续保留。
- 平板丢失时从手机撤销其设备密钥即可，不需要恢复或合并关系数据。

## 3. 设备职责

| 能力/数据 | 手机主机 | 平板伴随端 |
|---|---|---|
| 完整聊天与图片 | 保存/显示/发送 | 不保存、不发送 |
| Memory/Thought/Desire/AI Self | 唯一保存和写入 | 不创建第二套 |
| 模型、主动联系、Agent/MCP | 唯一执行 | 不执行 |
| 当前 App/屏幕状态 | 本机采集并接收远端事件 | 采集本机并上报 |
| 截图/轻视觉 | 按现有隐私 Gate 处理 | 仅在授权会话中采集，默认不落盘 |
| 桌宠 | 本地表现 | 主要表现端，可接收短期动作 |
| 配对身份 | 主关系密钥、设备清单、撤销权 | 独立 device_id、最小设备密钥 |
| 离线队列 | 接收去重/ACK | 仅短期加密事件队列，过期删除 |

## 4. 传输模型

正式跨网络同步不能依赖蓝牙或同一局域网。推荐使用“端到端加密的轻量公网中继”而不是云端关系数据库：

1. 手机生成一次性二维码/配对码和伴随设备密钥。
2. 平板加入同一关系但只获得最小权限，不获得完整关系数据库或主密钥导出能力。
3. 平板把小型加密事件上传到中继；中继只保存密文、排序/通知和等待 ACK。
4. 手机被推送唤醒后拉取、解密、按 `event_id` 去重，并写入短期 Awareness。
5. 手机确认后中继删除事件；过期未取事件也按 TTL 自动清理。
6. 手机发送给平板的宠物动作走反向临时队列，同样带目标设备与过期时间。

中继服务与推送项目应归属于用户可长期控制的账号。实现时可以由开发流程完成代码、部署和 App 接入，但创建/授权服务账号可能需要用户一次网页确认；用户不需要自行购买服务器或编写后端。

## 5. 最小事件契约

每条感知事件至少包含：

```text
event_id
source_device_id
source_device_label
observed_at
uploaded_at
expires_at
kind
activity_class
summary
confidence
sensitivity
content_hash / dedupe_key
```

约束：

- `event_id` 全局唯一；手机以它做幂等去重。
- `observed_at` 与 `uploaded_at` 分开，离线补传不能冒充正在发生。
- 普通活动 TTL 以分钟计；过期事件不进入当前 Prompt。
- 原始包名、验证码、密码、付款码、完整账号和高敏页面正文继续遵守既有本地遮蔽规则。
- 来源设备必须进入 System Facts/Recent Outcomes 和脱敏诊断，但不向模型暴露内部路径、密钥或任意日志。

## 6. 截图与轻视觉

- 常态优先使用当前 App、活动分类、Accessibility 可读摘要和屏幕锁定状态，不持续传输截图。
- 原始截图默认不落盘、不进长期 Memory、不进入普通备份。
- 屏幕捕获受 Android MediaProjection 授权会话限制；没有真实授权时不得假装已经看见。
- 第一阶段只做用户触发或已有授权会话内的“一次看当前屏幕”。需要跨设备识图时，图片应端到端加密临时传输或在平板做受控预处理，完成后立即删除；先验证价值再考虑低频自动化。
- 金融、密码、验证码、私密相册/文件等高敏场景继续停用截图或只上报粗分类。

## 7. 离线与失败语义

- 手机离线：平板保持本地桌宠基础待机，只短时缓存事件，不生成 AI 回复、不修改长期状态。
- 平板离线：手机照常聊天和自主运行，只是缺少该平板的新鲜感知。
- 中继失败：两端按事件 ID 重试；过期事件丢弃，不以旧活动推断当前状态。
- 手机恢复/换机：伴随设备默认重新配对或由恢复后的设备清单显式确认，不能让旧密钥自动夺取主脑身份。
- 任一伴随端都不能因手机失联自动晋升为 Active Brain；若未来需要灾备接管，继续走现有完整备份/接管流程。

## 8. 后续任务顺序

1. 当前批先完成无口令完整备份和恢复真机验证，确保手机主数据可靠。
2. Agent 自我系统读取先为 System Facts/Recent Outcomes 预留 `source_device_id / source_device_label / observed_at / executed_at`，但不等待多设备实现。
3. 建立设备角色、二维码配对、设备清单、撤销与诊断。
4. 接入中继、推送、加密事件信封、ACK、TTL 与去重；先只同步 heartbeat/当前 App 分类。
5. 手机把远端事件并入短期 Awareness；验证“平板看视频、手机聊天”场景。
6. 增加手机到平板的桌宠动作/短气泡指令。
7. 最后再评估一次性屏幕视觉和未来 MCP Outcome 的跨设备表现，不扩张为完整数据库同步。

## 9. 不可回归边界

1. 永远只有手机一份完整关系数据和一个 Active Brain。
2. 平板桌宠是表现/感知端，不建立第二套 Desire、Thought、Memory、Agent 或主动联系系统。
3. 添加伴随设备不等于恢复备份；普通备份不等于实时同步。
4. 中继只转发短期密文，不成为可读取聊天/记忆的云端主数据库。
5. 跨设备感知必须带来源、时间、TTL、敏感级别与去重键；过期/失败时明确降级，不虚构看见。
6. 以后若用户重新提出“平板也直接聊天”，应优先把输入远程转发给手机主脑，而不是复制数据库或开放多主写入。

## 3. 本轮确认要改：三项模型/API 配置

### M1 / 待修：第一聊天通道独立模型与力度

- 第一通道明确提供模型选择和独立力度，力度默认 High；第二通道最终回复保留自身配置和接口支持的档位。
- 现有“DeepSeek 内部模型”选择不等于完全缺少模型入口；重点是明确配置归属，消除共用力度及最终提供商归一化造成的耦合。
- 覆盖设置保存、普通生成、内部 Agent 规划、手动 DeepSeek 接续、失败重试、登记任务与重启恢复。不能只补 UI，不改调用链。
- 旧配置迁移保留原有实际行为；任务内的模型/力度归属一致。固定用途的专用判断不因新增设置被全局改力度。
- 工作模型仍独立，工作力度默认 Max，允许调整；不能把工作 Max 误当作第一通道或梦境默认。

### M2 / 待修：工作制作 API 支持跟随或独立配置

- 支持“跟随第一通道 / 独立配置”；升级默认沿用原跟随行为，工作模型/力度仍独立。
- 独立时 Key 与 endpoint 成对使用，保存在设备安全存储；设置、连接测试、实际请求与任务恢复核对同一配置归属。凭据不进公共仓库、普通存档或正文日志。
- 用户明确委托制作继续保留与普通聊天并行的既有行为；自主作品仍遵守空闲与提交栅栏。共用 Key 不等于必然串上下文，拆 Key 也不保证独立配额。
- 作品内互动、自主构思、完成通知和制作 Worker 分别确认通道；不能把所有 creative 请求统一切到工作 Key。
- 验证独立/跟随切换、修改配置后恢复、任务内参数一致性；不能混用一个配置的 Key 和另一个配置的地址。

### M3 / 待修：梦境跟随第一通道模型

- 用户已选择确认，“正文模型”在这项要求中指第一聊天通道 DeepSeek；梦境跟随该通道的模型及对应 Key/endpoint。
- 不再继承工作模型，不切到第二通道，不固定 Flash 或某个模型版本。修改第一通道模型后，后续梦境应使用新选择。
- 梦境原有 High 力度本轮未另行要求改变；不得擅自继承工作 Max 或把全部配置强绑在一起。
- 覆盖第二通道开/关、第一/工作模型不同、独立工作接口、模型选择变化及梦境中断重试；来源核验和成长语义保持。

配置事实与历史讨论见 [MODEL_CONFIG_FOLLOWUPS_2026-10-25.md](MODEL_CONFIG_FOLLOWUPS_2026-10-25.md)，以其中最新明确决定为准。

## 7. 执行顺序与反复收口方式

### 第一步：先修已确认项，按依赖分包

1. 游戏事实协议包：F1/F2，统一解包、目标身份、业务拒绝和有效状态；补真实执行/恢复入口反例。
2. 提交取消包：F3/F4/F5/F9，提交接受、停止目标、无回包恢复、通知队列与历史刷新衔接；同步验证 V1。
3. 游戏事件消费包：F6/F7/F8，把完整目标身份和读写事实贯通计数、报告、分享、约定、去重及 runner 目标登记。
4. 模型配置包：M1/M2/M3一并核对配置读取和恢复身份；V2独立验证后只作必要界面修补。

每包完成正常自查和反例对应回归，再进入下一包。不要每包扩大成全项目审查或反复生成 APK。若跨包共享契约变更，补跑受影响的前包回归。

### 第二步：固定候选源码，做七类复查

先按 G1–G7检查真实入口、调用者、提交者、所有消费者及既有用例；再做一遍跨类别时序检查。审查记录给出实际基线、触发条件、已有保护为何不足、影响范围与证据等级。

跨类别时序至少包括：

- 发送预检/接受/生成中的停止，新旧发送与迟到回包；普通/悬浮/通知互相接管。
- 模型/工具失败、断网、不回包、回包遗失、明确拒绝和未知结果；相同请求重试与新的明确请求。
- 游戏状态未落盘、只读核对、长参数和嵌套返回；跨槽、重复查询、纯查询结束与真实推进。
- 进程/Engine重建、前后台切换、恢复存档/设备主体切换；旧任务不能回写新状态。
- 重生成/删除来源、消息版本变化、日期跨天/回拨与来源入库顺序；成长、网页分享和反馈不重复。
- 作品发布/交付及播放队列中的中断，新任务开始后旧回调到达；UI更换后显示与数据事实一致。

### 第三步：发现、修补、按影响范围复查

新增问题先区分确认缺陷、条件风险和体验选择。确认后登记 ID、修补和复现用例；共享接口被修改时，重新检查所有受影响类别与调用入口。未修改且无新证据的部分不机械重复全量测试；新增时序、未覆盖消费者或失败结果应驱动下一轮检查。

每次修补更新候选基线和受影响范围，避免用修补前的审查结论覆盖修补后的源码。为修缺陷而做的接口收敛应保持小范围，不借机启动全项目架构迁移。

### 第四步：全量验证与同一源码的测试 APK

确认项闭合、条件风险有清楚结论后，运行仓库要求的源码门、桥接/原生、Dart分析、全量Flutter、存档恢复及Android检查，再统一构建测试APK。验收精确关联源码SHA、CI和包，不拿旧结果或中间候选代替最终源码。

### 第五步：设备反馈继续闭环

对悬浮输入/发送/取消、键盘/后台、真实游戏返回和长时间运行，结合用户设备结果继续定点复现、修补、回归。D1未取得证据前保留待验，不宣称已证明闪退根因。设备发现的问题进入对应 G 类，不随意推翻已验证的其他模块。

# 第二通道窄范围优化与语音阶段 Live2D 表演方案

日期：2026-10-21（Asia/Shanghai）  
状态：DESIGN ONLY；尚未实现、未运行本方案测试、未构建新 APK。

## 1. 本轮目标与基线

基线为 `catkiss62/ai-companion-build` 的 `agent/v042107-review-recovery` 分支，应用 v0.42.120+364 / `993a4471`。本轮仅编写方案和更新唯一总账。保留现有文字出现后的四拍表演：它先承接回复，覆盖内置 TTS 合成等待；在真实语音开始后，再增加对应台词的表情和动作。新增语音阶段不把现有四拍整体推迟到语音开始，也不机械重播原四拍。

第二通道只处理明确的尾流兼容风险，并补足判断该风险是否发生所需的计时。此前诊断中两次慢请求主要等待首输出；本方案不能解决中转排队或远端生成慢，也不承诺大幅缩短正常请求。

用户最新补充纳入：实际回复较长，语音阶段不能固定只有四拍；短句也不应为了凑四个状态而反复回落。现有四拍只继续用于先行动作，新增语音表演的段数另行安排。

## 3. Live2D：先行动作与语音表演分开

### 3.1 先行动作保留

- 回复进入聊天时，沿用当前四拍规划和播放方式、参数限幅、手动预设、原装动作及19情绪映射。
- TTS 合成期间，先行动作正常完成，之后保持已有持续表情和自主待机。不用延长或循环原四拍来填满等待。
- 无语音时，体验仍沿用当前路径。新增语音参数失败不能让已有效的原四拍计划一起失效。
- 原四拍和新增语音题在同一次 JEV 请求中返回。题量增加可能影响原规划耗时，必须记录并比较；不能把“请求次数不变”写成“首阶段耗时完全不变”。

### 3.2 语音阶段按语义重点安排，不固定四个动作

新增计划保存实际朗读文本的候选片段，每片段有“情绪”和“表达动作”两个 JEV 选择。表达动作允许自然说话/延续、不单独强调、短点头、侧头思考、短暂移开视线、小幅强调等；模型选择语义，代码把选择转换成菜菜已校准的安全参数及连续曲线。

候选片段由本地按朗读正文、段落、完整句和预计语音时长整理；标点只用于分段，不用关键词替代情绪判断。候选窗口不是“每窗口必须做一个动作”：JEV 可连续选择同一情绪、延续或无独立强调。实际朗读设置决定哪些动作描写/旁白会被读出，不额外强改朗读范围。

初版预算建议：

| 实际朗读规模 | 新增候选语义片段 N | 新增判断题 | 原四拍+语音题合计上限 |
|---|---:|---:|---:|
| 无待播放语音 | 0 | 0 | 39 |
| 短句、少量意思 | 1–2 | 2–4 | 41–43 |
| 普通多句回复 | 3–5 | 6–10 | 45–49 |
| 较长多段回复 | 6–8 | 12–16 | 51–55 |

这些是初版候选预算，不能用字符数机械规定表演次数。实施时结合现有语速估计划分候选窗口，控制总量最多8段；极长回复合并相邻完整句并用持续情绪/待机覆盖间隙，不只演前几秒、不因长回复追加另一轮 JEV。语速估计只用于预先分配预算，播放时间最终依实际 PCM 游标。

需要区分关键帧、动作和回落：一次点头可以含进入/峰值/回程多个帧；同一情绪也能保持一整段。参考视频的四个标签不代表必须产生四次独立动作。

例如“才、才不是刻意等你的呢，不过看到你回来还是挺开心的”，可有两个表达重点：前段保留嘴硬并短暂避开视线，转折后笑意/视线变柔。头或眼神可在局部强调后自然恢复，不强制中间两次切回正常脸，也不为了补状态再请求模型。

### 3.3 回落和长回复覆盖

- 回落属于本地曲线与参数所有权释放，不单列 JEV 问题，不占新的语义候选段。
- 局部动作结束时回到当前情绪和当前待机；回落姿势不等于清空情绪。
- 分段情绪只作临时表演覆盖，不回写消息的emotion字段；结束后交还该轮既有持续情绪，失效旧会话不得恢复自己的旧情绪覆盖新回复。
- 相邻片段可保持同一情绪并平滑衔接，不逐句回到中性，也不每个 TTS 小块都重新做起手/收势。
- 新增语音动作初版以表情、视线、小幅头身为主，复用现有限幅与安全通道。原装道具、奶茶、比耶、wink及整模大位移不因每个语音片段重复触发。
- 语义重点之间继续现有待机、呼吸和持续表情。长段保持不代表冻住模型；也不靠反复左右摆动或重复同一大动作填满时间。

## 4. 实际语音开始、进度与自然结束

1. 规划绑定消息ID、消息内容版本/朗读正文指纹、语言和舞台实例；播放再绑定现有 PlaybackIntent / playback lease。不能只靠消息ID拦同条重播的旧事件。
2. 真实 AudioTrack 开始后才进入语音阶段。发送消息、合成开始、音频生成成功、后续段入队均不能提前启动其动作。
3. TTS 队列保留实际朗读单元及候选语义片段的对应；在 enqueue 时携带可选片段元数据，原生按实际 PCM 帧范围登记。沿用原有分段、合并、预填充、格式校验、速度/音调及单轨播放方式。
4. 通过现有 playbackSnapshot 补充只读游标/段边界/播放状态。只在可见舞台与匹配播放会话存在时以低频读取，渲染侧本地插值；不每帧跨 MethodChannel，不新增音频等待或持锁读取推理。
5. 按实际播放帧进入语义片段；一个语义段可跨多个 TTS 音频块，一个合并块也可包含多个语义段。帧边界结合实际朗读片段长度估算内部位置；不宣称逐词或音素精确对齐。
6. 缓冲不足/暂停时，游标未前进就不追赶后续语义动作；保持当前基底并让短强调收住。改变语速后仍跟实际帧游标，不能用固定秒表继续跑。
7. 语音开始时先行动作若尚未结束，从当前渲染姿态平滑接入；不要求音频等它播完。若 JEV 较晚返回，语音照常播放；有效计划只从当前进度接入，跳过已过去的语音动作和过时先行动作。
8. 只有实际音频排空或明确停止，才结束语音阶段；“最后一个音频块已入队”不是播放结束。自然结束后短暂释放本阶段接管的参数，交还该轮既有持续情绪；不得误清手动预设或新动作。

现有首次 enqueue 等待原生启动这一机制保留，不把它误记为原有启动缺陷。需要补的主要是后续真实片段进度与新增动作衔接。

## 5. 静音、中断与交互边界

| 情况 | 计划行为 |
|---|---|
| TTS关闭、自动朗读关闭 | 保留原四拍和待机；没有实际语音意图就不准备新增语音题或启动语音阶段 |
| App朗读音量或系统媒体音量为0 | 不启动或释放新增语音动作，保留原有视觉反应；不把来电静音/勿扰一概当成媒体无声 |
| 播放中静音后恢复音量 | 静音时停止额外语音强调；恢复且会话仍有效时，从当前播放位置接入，不补演已过去的片段 |
| 合成中取消 | 撤销该 PlaybackIntent 的语音呈现资格；晚到音频/计划不得让语音表演复活；先行动作沿既有停止策略 |
| 点击停止语音/音频播放失败 | 立即失效该语音阶段；短平滑释放自身参数，不强制整张脸变正常，不影响新主人 |
| 新用户消息、新回复或重生成 | 旧消息/版本/播放租约失效；旧段回调与旧释放命令不可覆盖新表演 |
| 同条语音重播 | 新播放lease、新进度；可复用匹配正文版本的计划，不能沿用旧计时；不重复购买JEV |
| 历史消息手动朗读、外语朗读无匹配计划 | 保留现有语音/口型和基础待机；初版不为此追加JEV，也不把当前新回复的动作套到旧消息上 |
| 摸头、手动原装预设 | 现有显式交互优先；被占用时跳过当前语音强调，释放后从当时播放进度继续，不重播漏掉的动作 |
| 切页、隐藏舞台、切后台、切模型或导入存档 | 注销可见舞台的语音动作订阅并失效旧舞台实例；不为了动作功能改变既有后台语音策略；返回后仅匹配当前有效播放会话 |
| 其他宿主/预览/提醒声音 | 不启动普通聊天舞台语音表演；既有进程级host/lease和消息关联有效后才接入 |

嘴部开合始终由现有真实PCM口型拥有，新增动作不写 mouth-open。不同主人的清理仅释放自己取得的参数。音量/静音判断不能新增每帧系统查询。

## 6. JEV调用量、失败与兼容

- 原四拍仍最多39题；语音阶段每候选段2题，同一次 chooseMany，总题数为 `39 + 2N`，N=0–8，最多55题。原模型参数不齐时实际原题数可能更少。
- HTTP规划请求仍每条回复一次，不按音频块、动作帧或回落追加请求，不额外先调用大模型拆句。
- 先前“39→43”只覆盖短回复/少量片段的估算。按用户最新两阶段且长回复要求，不能承诺所有回复都43题；长回复55题相对39题是题数约增加41%，不等于费用增加41%。
- token开销含新增片段上下文和选项，以现有caicai_speaking_motion的实际usage/cost/elapsed统计；不根据题数直接推算费用。保留现有8秒请求超时，不为动画放宽长等待，不加失败重试或DeepSeek动作兜底。
- 新题为可选扩展：新增字段缺失/无效只跳过对应语音表演，不丢弃有效的原四拍答案，不改JEV既有赢家/概率规则。
- 语音计划仅绑定当前正文、语言和有效期暂存；不写入人格/记忆，不更改数据库schema、存档协议或已有世界书。停止、导入或版本失配后不能复用过时计划。

## 7. 第二通道：只做有界尾流收尾与必要计时

### 7.1 窄范围收尾

给第二通道纯正文请求显式启用适配，默认关闭；第一通道、Agent工具规划、带工具请求及JSON判断沿原有路径。

- 仅在当前请求的受支持单choice已返回非空正文、`finish_reason=stop`，且无已发出/未完成工具调用及机器协议碎片时启动收尾窗口。
- 先完整消费带stop的同一事件中的正文和reasoning，再进入窗口。首个合格stop启动固定短窗口，初版建议2秒；usage、重复stop和keepalive不延长窗口。
- DONE或正常断流先到则立即结束；窗口内正常接收尾部usage，窗口到期后主动结束本请求并按已有候选校验/提交处理。
- 如果出现stop后追加正文/工具碎片、多choice或不支持的终止类型，退出该快捷适配并回到既有处理，不截断内容。异常与取消仍走原有路径；用户取消优先于收尾计时。
- `length`、内容过滤等终止不能被当作正常stop；缺失finish_reason不能套用2秒窗口。首次输出前和正常生成中的120秒无进展规则不改变。
- 来不及取得的usage记为未知/缺失，不伪造0消耗，也不为补统计再发请求或保留后台网络尾流。

此改动只处理“内容结束但中转连接迟迟不结束”；没有合格stop时维持原行为。普通/主动/修正正文使用同一可选策略，具体只在相应纯正文调用入口启用，不根据endpoint字符串宽泛影响其他请求。

### 7.2 最小计时

在已有请求诊断上增加：finishReason到达、候选流结束、正文接受/提交时间及结束原因（DONE、自然断流、客户端尾流到期等）。保留已有首进展/首正文/总耗时。

用每次attempt的单调计时计算首正文前等待、结束信号后等待和候选结束至提交耗时；重试分别编号，不能混算。客户端主动结束不能标成远端自然关闭。只记录时长/原因/身份，不新增正文、Key或完整网络请求持久化。

本轮不删除事实/完全重复检查，不改变只记录的文风检查，不改第二通道思考力度、重试次数、DS兜底、上下文、候选缓存显示和提交/记忆事务，也不扩大Agent权限。

## 8. 实施顺序与验收

1. 对齐+364代码，保留本地已有修改；登记实施前唯一总账。先独立完成第二通道窄修及模拟SSE回归，可独立回退。
2. 先接只读播放进度和片段元数据，验证正常播放、预填充、速度变化、缓冲、停止及跨宿主租约；不改推理/PCM调度。
3. 在原四拍同批追加可选语音题，完成分段表演协调、静音/取消/晚到处理；不能把四拍重新定时来代替已授权的两阶段设计。
4. 统一定向检查、相关原生与Flutter回归、完整CI、存档恢复和同签名APK；新增语音效果与实际JEV成本仍需真机验证，测试数量以实际结果记录。

必要自动场景：

- SSE同帧正文+stop、DONE先到、usage尾包、stop后只剩keepalive、不发stop、length、工具片段、多choice、取消与超时竞争；正文不截断、usage不重复、只提交一次，DS/工具路径不改变。
- 原四拍保留；N=0/1/2/多段/8段上限；无独立动作、同情绪延续、局部回程不清空情绪；原题有效而新题缺失时仍有原表演。
- 先行动作在合成等待时播放；实际音频开始才接第二阶段；后段入队不提前表演；停顿不跑空，最后入队不提前收尾；晚到计划只从当前位置接入。
- 关闭TTS、App音量0、系统媒体静音与恢复、合成中取消、播放中停止、重播新lease、新消息/重生成/切页/后台/换模型/导入、手动预设/摸头与其他宿主抢占；旧回调和旧释放不得复活或覆盖新主人。

真机重点：短句是否只有合适的表达重点而非频繁归零；30秒以上长回复是否全程有自然基底且后半段仍有语义响应；当前先行动作幅度/节奏是否保留；音频启动是否无新增等待；实际题数/token/cost和JEV延迟与原版对照。视觉自然度不能仅靠数值合法或CI通过验收。

## 9. 交付边界

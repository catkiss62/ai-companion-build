用户强调主要动机是让伴侣能及时修改自己的上层功能与逻辑，缩短“发现小问题→修改→可使用”的周期，而不仅是减少安装包下载；已在手机使用插件式DSh，但没有指定具体安卓分支。不将桌宠动画来源仓库或某个DSh安卓宿主擅自认作用户安装的版本。

基于这个目标，建议由“暂不全量重构”细化为“自我迭代值得单独评估局部插件层”：稳定宿主管数据所有权、发送/取消、权限及安卓原生能力；可替换层先承载互动小功能、内容整理/选择、表达或展示策略等上层逻辑。先以一项可隔离、有版本和回退的模块验证AI修改→自动验证→试用→回退的完整过程。现有HTML小作品制作/预览管线可作为部分基础，不能直接当作已有通用自修改能力。

插件化、热更新能力与自我修改的执行权限分别设计。插件只使用宿主公开接口，新增原生接口仍通过宿主更新；不要让插件直接改正式库或撤掉未知写/取消/来源保护。具体运行时、首个模块、自动生效范围和验收标准留在未来独立设计阶段，本轮不安装DSh/OTA运行时、不替换Flutter/原生架构，不挤入九项及模型设置修补。

用户澄清：希望在项目内直接让 AI 修改、验证并试用逻辑，免于每个小改动重新构建；不因“原生有机会优化”接受专用 App 的必然优势，也担心数百轮修改后整体迁移引入大量回归。梦境与作品都需要读取记忆并将真实结果送回记忆。当前仅评估，没有授权启动框架迁移或通用自修改运行时。

架构判断：普通聊天可设计为一次模型调用、未挂工具；需要执行工具时再进入 Agent 路径，通用插件宿主并不强迫每次闲聊都规划/执行。现有 DSH 安装是否已有符合本项目要求的现成模式尚未核查，不能承诺安装一个开关即可得到全部陪伴行为。官方开源框架是 `deepseek-ai/deepseek-harness`；所查 Android 封装位于 `DSH-APP/DSHA`，不能将不同维护方及其兼容承诺合并称作同一个官方产品。框架源码可复用，不必自行重写整个 DSH。

插件读写记忆在技术上可行。DeepSeek Harness 官方已有独立的存储服务/JSON、SQLite 后端及领域数据接口；但这些是存储能力，不自动提供本项目的经历来源、成长语义、用户/自身区分与恢复规则。可以把本项目的统一记忆服务作为宿主服务或基础插件，由梦境/作品调用，避免每个功能维护互不相通的记忆库。若从零开始、优先目标是自我迭代，成熟框架＋自定义插件是合理路线；当前已有 Flutter/Kotlin 项目迁入 DSHA 则需接口适配、部分代码重写和数据/行为迁移，并非重新打包目录。

源码证据：`creative_inspiration_engine.dart` 通过 `DreamStore.usableInsights`、`DreamMaterial.collect`、`DreamStore.prompt` 读取可用自我理解及真实经历，构思保留来源和独立动机；`creative_workspace.dart` 已通过 `window.companion.saveState/choose/reveal/report` 把网页作品与宿主连接，但这是特定作品桥，不是现成通用插件运行时。`dream_store.dart:262` 的提交事务核对运行身份、预期旧状态、消息指纹及原始来源后才更新状态。上述边界证明可以保留数据服务并替换上层策略；不证明所有记忆链路已经完整、无 bug 或可无成本迁移。

候选渐进路线：先外置提示/规则（改动较小）；进一步把梦境整理策略做成可更新插件（首次需执行环境和接口，属中等规模工程）；完整作品制作涉及持久任务、预览、发布及交付，成本更高；整体迁入 DSHA 还涉及聊天/记忆迁移、手机原生能力及生命周期，属于大规模迁移。插件可以是核心功能，不局限外部小功能。保留当前宿主并抽一项策略，不等于将其余功能永久锁在原生代码。

梦境候选接口：统一记忆服务提供带来源 ID 和版本的材料快照→插件给出结构化修订建议→宿主重核来源/状态并一次提交→后续聊天及作品通过同一服务读取可用理解。作品候选接口：按需查询记忆/理解→制作与预览任务→宿主核实完成结果→记录真实作品事件及互动来源→按原记忆流程选择是否形成长期记忆；不是把整个作品或插件自称完成直接写成事实。任务身份/来源核验和失败后不写半份结果的语义必须保留。统一服务若本身也是基础插件，仍应是单一数据所有者，并非必须硬编码在 APK。

验证建议：先对固定材料只输出建议、不写正式记忆，检查与旧版本的差异；覆盖删除/重生成来源、重复提交、导入旧存档、任务中断、插件升级期间的任务版本。保留旧实现回退；插件版本回退不自动撤销已经写入的成长内容，需将输出版本/来源关联，并设计修订或恢复快照。测试可降低风险，不能预先保证全部稳定，也不能只验证 JSON 可解析。

本地修改与管理建议：可设计 App 内编辑草稿、校验、保存版本、切换生效与导入/导出包；在途任务固定所用插件版本，新任务才使用新版本。DSHA 插件与自建宿主插件必须分别匹配运行时/接口，不能承诺同一压缩包直接通用。该管理器尚未实现。GitHub 不必成为每次本地修改生效的前置条件；但本地版本只防误改，卸载/设备损失仍需设备外备份。建议稳定插件源码周期同步 GitHub，插件包及对应版本纳入存档备份；聊天记忆与 Key 不随源码推入公开仓库。

官方框架及存储资料：https://github.com/deepseek-ai/deepseek-harness ，https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/storage 。本轮仅记录决定与方案，未做插件抽离、运行时改造或新构建。

## 最新补充：以低成本 AI 维护为目标，评估多数业务插件化

用户强调最关心现有思路是否不利于后续 AI 修改，希望基础框架＋业务插件能更容易纠错、省上下文和管理，而非只在当前 App 外围加几个插件。建议相应调整为：可将多数业务逐步插件化作为长期目标；不以“内置”本身证明现有方案错误，也不以“专用 App 可优化”证明值得继续扩大内置耦合。目标是稳定的小型宿主/公共服务加业务插件，公共记忆/模型/任务服务也可作为基础插件加载，但接口和数据归属必须稳定。

本轮定点检查的证据：`app_database.dart` 21,032 行/104 个 import；`chat_controller.dart` 2,113 行/58 个 import；`durable_generation_runner.dart` 2,859 行/78 个 import，直接引用 Agent、游戏、作品、记忆等业务。行数不证明具体缺陷，结合跨业务依赖则支持进一步分离职责。梦境四个主文件已有调度/契约/材料/存储分工，具备局部抽离的基础；并非整个项目完全没有模块化，也未在本轮完成依赖图或完整迁移审计。

纠错收益取决于接口清楚、单模块可复现和回归、公共服务不被任意绕过；插件化本身不能修复跨模块竞态。开发 Token 有望随需要阅读的源码和历史范围缩小而减少，但首次迁移及接口维护成本会上升，尚无量化对照。伴侣运行时的 Token 取决于按需注入，不能每轮把所有插件说明与状态全部塞进提示词。插件数量和说明书增加也可能增加上下文成本。

需要分别规划源码模块化与动态更新：前者在现有 Flutter/Dart 中就能改善边界和检索；后者还需宿主执行环境、插件接口、版本/依赖、任务版本固定、验证及回退，现有 AOT Dart 代码不能靠移进 plugin 文件夹就成为免构建热更新。无需自行复制实现完整 DSH，可复用官方开源运行时或在现有宿主接入较小的可更新运行层；选择前还需核验当前原生能力、UI、存档兼容和成本。

顺序建议仍先完成已确认九项与模型配置修补；后续架构阶段先梳理共享记忆/模型/任务服务，选梦境策略做一条可按版本验证和回退的完整链路，再逐步迁移其他业务。完整作品、游戏与后台链路属于后续更大范围。此建议支持多数业务未来成为插件，不等于当前已决定整体迁入 DSHA，也不启动本轮全量重写。本轮仍只记录分析和最新梦境模型决定。

## 补充校准：插件架构与“每轮调用 Agent”

用户追问“框架插件不会逼每轮调 Agent，反而更容易控制谁何时上场”是否真实。应有条件表述：官方 DSH 的标准组合由 `dsh-agent-loop` 驱动每个对话 turn/step，带入当步可见工具定义，并执行模型实际提出的工具调用；进入该循环不等于额外发起一次独立规划请求，也不等于必定执行工具。完全不经过 Agent 驱动的轻量聊天路径在架构上可另行设计，不能把这种可行性说成所有安装默认已有的行为。

当前项目已有 `on_demand_agent_entry.dart`：说话模型在已有请求里可选 `agent_request`，未选时不增加该规划请求；入口只授予发现/读取，游戏和作品等实际操作保留既有授权入口。`agent_tool_registry.dart` 已集中列出能力、风险、用户/自主可见性。因此不能将现有 bug 统一归因为“内置功能导致每轮 Agent 失控”。进一步插件化可以改善工具可见范围、统一入口和单插件验证，但需要具体设计；模型语义误判、参数/结果核验、重复执行、取消与迟到回写、原生悬浮窗生命周期分别有不同修复点，换包装不会自动修复。

官方默认循环依据：https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/README.md ，https://deepseek-harness.github.io/deepseek-harness/en/reference/agent-lifecycle 。本轮仍无运行代码变更。
